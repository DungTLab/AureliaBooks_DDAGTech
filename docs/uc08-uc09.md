# UC08 / UC09 implementation

## Profile rules

- Customer identity is resolved from the local user ID or verified Google subject, then checked against the current database role and active state. No owner ID is accepted from forms.
- Editable: full name, gender, avatar. Existing DOB and phone are immutable; a Google account may complete each missing value once. DOB is optional and must be in the past; no age rule is applied. Profile mutations lock the owner row, preventing competing requests from overwriting a completed DOB. The unique phone index protects competing phone submissions.
- Password changes verify the stored BCrypt hash and use the same complexity and 72-byte UTF-8 limit as registration. Google accounts without a local password continue using Google. Successful password changes expire registered sessions after commit and invalidate the submitting session.
- Avatar uploads: maximum 2 MiB, actual PNG/JPEG decoding, maximum 16 million decoded pixels, re-encoded PNG thumbnail <=512 px. Private owner-only retrieval. New files are removed on rollback; old managed files are removed after commit. Remote Google avatars are never deleted.
- `AVATAR_DIRECTORY` defaults to `./uploads/avatars`. Mount this directory persistently when deploying; it is ignored by Git. Filesystem storage and the in-memory session registry target the existing single-instance monolith.

## Addresses

Routes under `/profile/addresses` provide list, create/update, default selection and soft deletion. All mutations lock the owner row first; this serializes quota/default changes. There can be at most five active addresses and exactly one default when the active list is nonempty. Deleting the default promotes the oldest remaining active address.

Required fields: recipient, Vietnamese 10-digit phone starting with 0, province, district, ward, detailed address and one of NORTHERN / CENTRAL_HIGHLANDS / SOUTHERN_MEKONG. No password hash or owner entity is returned to the view. Every POST uses CSRF.

## Database upgrade and checkout handoff

Fresh databases use the synchronized `schema.sql` and `docker/initdb/01_schema.sql` (still 21 tables). Existing databases require the one-time, additive migration `docker/migrations/20261008_uc09_address_order_link.sql`; do not rerun the reset-capable initialization script on existing data. `ddl-auto: validate` does not apply this migration.

Dictionary addition:

| Table | Field / key | Meaning |
|---|---|---|
| orders | shipping_address_id, nullable BIGINT | Source address selected at checkout; NULL only accommodates existing orders. Shipping snapshot remains unchanged. |
| shipping_addresses | unique (id, user_id) | Composite reference target that verifies address ownership. |
| orders | FK (shipping_address_id, user_id) | References shipping_addresses(id, user_id), restricting physical deletion. |

Checkout is not implemented in this branch. Its assigned developer must:

1. Resolve the authenticated CUSTOMER and require a completed account phone before accepting checkout; otherwise send the customer to `/profile`.
2. Lock the same users row, select an owned active address (default when none is explicitly selected), and save its ID to `orders.shipping_address_id` with the immutable shipping snapshot in the order transaction.
3. Never accept an arbitrary address ID without ownership/active checks, or silently set the link to NULL for a new order.

Address deletion blocks orders not DELIVERED/CANCELLED. Existing unfinished orders with a NULL source link conservatively block deletion of that customer's addresses because snapshot text cannot reliably establish identity. No links are guessed or backfilled. Editing an address never modifies an existing order snapshot.

## Verification

Unit and MockMvc tests cover immutable fields, Google phone completion, password validation, session invalidation, image boundaries, IDOR, CSRF, form rendering and address invariants.

`ProfileAddressMySqlTest` is opt-in (`-Duc08.mysql=true`) and refuses databases without the `uc08_qa_` prefix. Run it with an explicitly isolated datasource. It exercises concurrent creation, FK ownership, unfinished/finished/legacy orders and Google phone persistence. Normal tests skip this class rather than access a developer database.

Google's real token exchange and a live checkout are outside these test receipts. The MockMvc UI captures use synthetic fixture data, not production users.
